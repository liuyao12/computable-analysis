\chapter{Formalization Roadmap}

The blueprint is a map, not a second proof. Figures show the computation;
pseudocode names the invariant; Lean carries the details.

The focused Lean entry point for this route is
\texttt{ComputableAnalysis.CalculusFoundation}. It collects the chapter
imports without requiring an agent to depend on the full 100-theorem
benchmark catalogue.

As an integration check, this entry point builds under Lean 4.33 with all 91
imported modules. The focused entry point is therefore the recommended first
compile test for a new proof, while individual chapter modules remain useful
for fast iteration.

\section{Admission rule}

Include a result when it yields a rational certificate, a shrinking `realRaw`,
a valid `real`, or an overlap between independent computations. Reuse routine
finite combinatorics from the library.

Use one representative for each computational pattern. A scalar multiple,
sign change, or routine composition is a transport of an existing certificate,
not a new chapter theorem. If a function is naturally piecewise, split the
domain into its finitely many pieces and assemble the separate integrals. For
example, $|x|$ on $[-1,1]$ is two affine-cell integrals joined by a finite
sum. The foundation should formalize the assembly rule once and spend new
proof effort on genuinely new evaluators, estimates, or equivalence edges.

\section{Order}

\begin{verbatim}
foundations -> circle/trigonometry -> integral algorithm -> effective FTC
            -> power series -> exponential/logarithm -> linear ODEs
\end{verbatim}

\section{Style}

Use only `realRaw` and `real` when the distinction from standard real numbers
matters; leave implementation names and proof details to Lean.

\section{How to formalize a new theorem}

Start with the computation, not with a completed function space:

\begin{verbatim}
domain -> finite evaluator -> rational enclosure -> validity -> equivalence

raw computation A ----\\
                     overlap at every stage -> abstract real/function result
raw computation B ----/

For inverse functions, the same rule applies to the forward branch: use the
representation whose finite schedule is convenient for search, and attach a
pointwise equivalence edge to the semantic evaluator.  This is the intended
way to maintain the project's chain of interchangeable computations.

derivative/area claim -> cell certificate -> mesh refinement -> endpoint overlap
\end{verbatim}

For adaptive evaluators, keep the native computation schedule visible.  The
scheduled interval-regularity contract can be consumed directly when a
requested-stage containment proof is available; an identity schedule is the
ordinary special case.  This prevents stage changes from being mistaken for
definitional equality of computations.

\lean{ComputableAnalysis.ScheduledIntervalRegularOn.toIntervalRegularOn_of_requested_stage}
\lean{ComputableAnalysis.ScheduledIntervalRegularOn.toIntervalRegularOn_of_identity_schedule}
\lean{ComputableAnalysis.IntervalRegularOn.toScheduledIntervalRegularOn_identity}

For a new real-valued quantity, add one `realRaw` evaluator and prove its
order, nesting, and shrinking-width obligations.  If another evaluator is
already available, add one finite overlap edge to it; the abstract `real` or
function layer can then use the maintained chain of such edges.  For a
function, keep the evaluator total but attach its rational domain and use the
domain proof at every call.  For an integral or derivative, expose the finite
cell estimate and its error budget before stating the limiting-looking
corollary.  Classical completeness, Lebesgue measure, and unrestricted
measurability are not implicit fallbacks: if a result needs one of them,
state a computable proxy or record the bridge as a separate theorem target.
